## Coming soon

So far only in the staging test channel (`channel = "staging"` in `/etc/lux/lux.conf`).

### New
- **Scrolling like on macOS: touchpad inertia and a smooth mouse wheel** (`luxos-desktop` 70, `luxos-terminal` 1.3.0-6, `luxos-i18n` 74, `luxos-docs` 61): after a quick swipe on the touchpad the content keeps moving and slows down smoothly; the mouse wheel glides to the new position in 200 ms instead of jumping (more notches during the glide add up, the distance is the same as before). It works in GTK 3 apps (Files, Text Editor, Settings, Store, LuxOS apps in LSL, Xfce), in Terminal, Firefox and Mail. Moving the pointer with the touchpad, a tap or a click stops the glide (GTK alone would keep going). A new GTK module `luxos-scroll` (xsettings `Gtk/Modules`, re-added by `luxos-session` at login if something replaced the value) animates the wheel only in a real GtkScrolledWindow – an app's own scroll handler, Ctrl/Alt/Super+wheel (zoom), the touchpad, nested lists and programs with their own scrolling (games, Blender, Steam, Maps, `htop`/`mc`/`less` in Terminal) are unchanged; with animations off (reduced motion, Battery Saver) the wheel jumps as before. **Settings › Scrolling** (`luxos-scrolling`, a new window in LSL, also `luxos-scrolling status | kinetic on|off | smooth-wheel on|off`) has the switches **Smooth scrolling with the mouse wheel** and **Inertia on the touchpad** and a link to Mouse and Touchpad settings; changes apply right away, also in open windows (`~/.config/luxos/scrolling.conf`). Terminal scrolls its history by pixels through GtkScrolledWindow (VTE `scroll-unit-is-pixels`), so the touchpad scrolls smoothly and with inertia. Firefox on X11 without XInput2 got only wheel notches from the touchpad – the session now sets `MOZ_USE_XINPUT2=1` (`/etc/X11/xinit/xinitrc.d/50-luxos-firefox-xinput2.sh`, from the next login) and the Firefox defaults turn on the pan gesture with inertia. Turning inertia off also applies to Firefox and Mail (the end of the gesture arrives 250 ms later, so the speed is zero). Tests `test_luxos_scroll.py` with real XInput2 events from a private Xorg (inputtest driver, like xf86-input-libinput including the event after the fingers lift): inertia and deceleration, stopping by touch and tap, turning it off also while an app runs, smooth wheel with the same distance, Ctrl+wheel, an app's own handler, a nested list, reduced motion, VTE by pixels, WebKitGTK and a real Firefox 160; Terminal: the wheel in the history and in `less`. To check on a real touchpad: the speed and length of the glide, and edge scrolling (the LuxOS default).
- **Switching workspaces slides to the side like on macOS** (`xfwm4` 4.20.0-2.4, `luxos-desktop` 69): when you switch workspaces (Ctrl+Super+arrow, Ctrl+Super+number, the workspace switcher in the top bar) the windows of the old workspace slide out and the new ones slide in – the next workspace from the right, the previous one from the left, also when jumping over several workspaces and when wrapping from the last workspace to the first in the direction of the key. The wallpaper, desktop icons, windows on all workspaces, the top bar, the Dock, menus and notifications stay put. The slide takes 420 ms with a gentle start and a soft settle, input is never blocked and quick repeated switching continues smoothly, keeping its speed, without queueing (also going back during the animation). A window carried along to another workspace stays in place. With several monitors each monitor slides on its own. Without the compositor and with reduced motion (Gtk/EnableAnimations off) workspaces switch instantly as before; options `/general/workspace_slide` and `/general/workspace_slide_duration` in the xfwm4 channel. The slide does not follow touchpad fingers yet (LuxOS has no touchpad gestures yet).

Widgets: clock with weather from the Weather app, system status with processor, memory and disk arcs, now playing music with controls, moon; a click opens Clock, Weather, Calendar or System Monitor. **New Clock app** (`luxos-clock-app`): alarm (weekdays or once, Snooze/Stop, rings even with the app closed), world clock, stopwatch with laps and timer. **System Monitor** sorts the list by name, processor or memory (click a column header, the choice is remembered). **Fixed:** the Wi-Fi icon in the bar stayed black even with white text – the network applet now runs as a StatusNotifier item (`nm-applet --indicator`) and the bar colours it like the other icons. - **Less memory in every session** (`luxos-tweaks` 14, `luxos-companion` 6, `luxos-desktop` 65, `luxos-guard` 7): the kernel reserve `vm.watermark_scale_factor` is back at the default 10 – on a computer with 16 GB of RAM, `free` showed ~0.5 GB more "used" memory because of an oversized kernel reserve, although no program was using it (zram, earlyoom and everything else stay the same). The Lux Guard session helper (`luxos-guard-agent`) is now a small LSL program: ~0.5 MB instead of ~12 MB of Python for as long as you are logged in; question dialogs, notices and "Run in Sandbox" / "Move to Trash" are still done by Python, but only for a moment when something happens, and a helper started before the update switches to the new version by itself (no logout). `luxos-hub` prepares the Emoji & Symbols window on first use (~7 MB less in every session; the first opening takes ~0.5 s, later ones are instant as before). LuxOS Companion frees loaded calendars after the phone disconnects. In a clean session (4 GB VM, average of two measurements, no apps) `free` "used" 2 min after login 817 → 797 MiB, after 6 min 796 → 771 MiB; boot and login just as fast.
- **LuxOS starts with Secure Boot on – nothing to turn off on an ordinary Windows computer** (new `luxos-secureboot` 1.0.0-1, `luxos-care` 16, `luxos-installer` 36, `luxos-i18n` 68, `luxos-docs` 54, ISO, kernel `linux-luxos` signed with the LuxOS key): until now firmware with Secure Boot on refused the ISO and the installed system ("Access Denied") and the only advice was to turn Secure Boot off – not acceptable for people coming from Windows and for companies (and BitLocker then asks for its recovery key). LuxOS now starts through a **Microsoft-signed shim** (the same file as Fedora, signed with Microsoft UEFI CA 2011 and 2023 – older and new computers), which starts the systemd-boot menu and the kernel signed with the **LuxOS key**. The key is added to the computer once, on the first start from the USB stick: blue shim screen → OK → any key → MokManager **Enroll key from disk** → disk → `LUXOS_ENROLL_THIS_KEY.cer` (right at the top) → Continue → Yes → Reboot (11 keys, no typing); the installed system then starts directly. If the USB stick was started with Secure Boot off, the installer prepares the key itself and shows a one-time 8-digit password – on the first start just Enroll MOK → Continue → Yes → password (`SECUREBOOT_ENROLL=auto|yes|no`). Existing installs get shim with an update: `EFI/LuxOS` (shim, MokManager, signed systemd-boot) is added to the EFI partition, the "LuxOS" boot entry goes first and the old one stays as a backup until LuxOS has started once through shim; without Secure Boot nothing changes. To turn Secure Boot on afterwards: `sudo luxos-secureboot enroll` (MokManager waits 60 s instead of 10 s), state: `luxos-secureboot status`. DKMS drivers (NVIDIA, Broadcom) load with Secure Boot without any extra step; `enroll` also adds the computer's DKMS key. System snapshots start with Secure Boot too (the kernel is signed in the package); older snapshots and the previous kernel from before signing show "- needs Secure Boot off" in the menu and LuxOS Recovery then starts with the signed kernel. Only the maintainer has the private key (the Safe); CI builds unsigned packages and signing happens before publishing (`scripts/sb-sign.sh`; `publish-repo.sh` refuses an unsigned kernel). Tested in QEMU with OVMF and Microsoft keys (test key): ISO 1.0.1 refused; new ISO → key enrollment → live system with Secure Boot; installation and start with Secure Boot; snapshot start; out-of-tree module unsigned and signed with a DKMS key in MOK; a 1.0.1 install upgraded with the packages starts without Secure Boot through shim and, after enrolling, with Secure Boot on; firmware with only CA 2011 accepts shim, without the third-party CA (Secured-core) it refuses it – explained in the manual. Guide with screenshots: the **Secure Boot** manual page and *Secure Boot: first start* on the website; plan for LuxOS's own Microsoft-signed shim (no MokManager step): `docs/proposals/secure-boot.md`. Also fixed along the way: `sbverify --cert` reports "OK" even for foreign chains (Microsoft's shim) – the check now requires the LuxOS certificate in the signature.
- **Mail: write, reply, forward and send mail – and messages that look like messages** (`luxos-mail` 1.0.0-9, `luxos-i18n` 67, `luxos-docs` 52): Mail now sends mail (SMTP), not only reads it. **New Message** (Ctrl+N), **Reply** (Ctrl+R), **Reply All** (Ctrl+Shift+R) and **Forward** (Ctrl+Shift+F, with the original attachments) open a message window with From (account picker), To/Cc/Bcc with address suggestions (people you wrote to and senders in your local mail), subject, text and attachments (button, Ctrl+Shift+A or drag and drop; list with size and ×, a warning above 25 MB). Send with the button or Ctrl+Enter; replies quote the original ("On … wrote:" with `>`), keep the thread and mark the original as answered (forwarded) on the server. A signature per account, `mailto:` links with subject and body. **A written message is never lost**: it is saved on the computer 1.5 s after every change (after a crash the window comes back), to Drafts on the server after 30 s (replaced by each new version, removed after sending); closing asks "Save this message as a draft?". Without a connection the message waits in the **Outbox** and is sent automatically (30 s, 1 min … at most every 15 min, at once when the network is back); permanent errors (refused recipient, sign-in, message too large) say exactly why and nothing is sent, an Outbox message stays "Not sent" with the reason and a notification. A copy goes to Sent on the server – except for Gmail and Microsoft, which save it themselves. Own SMTP client in LSL: implicit TLS 465 and STARTTLS 587 with certificate and SNI checks, AUTH PLAIN/LOGIN, XOAUTH2/OAUTHBEARER with Google, Microsoft and LuxAI tokens, SIZE checked before sending; RFC 5322 messages in UTF-8 (RFC 2047 headers, quoted-printable/base64, RFC 2231 file names, no Bcc header). **Received mail is shown properly** (links were not clickable and formatting was poor): messages are shown in a locked-down WebKitGTK (already part of LuxOS) – HTML mail with its layout, colours, tables and attached pictures (on white paper also in dark mode when it has its own colours); plain text with clickable links, quotes as indented blocks with a coloured bar, a dimmed signature and ASCII tables in monospace. Links open in your browser (mailto: in a new message) and show their real address on hover. Remote images and tracking pixels stay blocked until **Load Images** or **Always from <sender>**; scripts, event handlers, forms, iframes, external styles and dangerous links are removed and the message page forbids network access (Content-Security-Policy), JavaScript off, no cookies. Attachments: Open / Save As…, picture previews under the text; Ctrl+F finds in the message, Ctrl+P prints, Ctrl+plus/minus/0 zooms. Ctrl+R is now Reply (like Mail on macOS); get mail with F5 or Ctrl+Shift+N. Also fixed: after a background sync rebuilt the message list, the list lost the keyboard focus and the arrow keys did nothing.

The model can write `"mode": "list"` for a short self-check. Mail now signs in with the provider like Thunderbird (OAuth 2.0 for native apps, RFC 8252): for a recognised provider the Add Account window shows one main **Sign in with Google** / **Sign in with Microsoft** button (neutral text, no logos) and the password field disappears (for Google it stays under **Use an app password instead**). Google Workspace and Microsoft 365 on your own domain are detected by MX. - **Mail – LuxOS's own lightweight mail client with instant new-mail notifications** (new `luxos-mail` package in `[luxos-apps]`; phase 1: reading and notifications): a small background program `luxos-mail-service` (no GTK, about 17 MB, starts with the session) keeps one connection per account and thanks to **IMAP IDLE** the server announces new mail itself – a **"New mail from …"** notification with subject and preview arrives within a second, **Open** opens Mail right at the message, several messages give one summary, already read or announced messages stay quiet and Do Not Disturb is respected. The unread count shows on the Dock icon. **The window** has three columns like Mail on macOS (mailboxes, message list with unread dots and attachment clips, message), light and dark, opens in 0.2 s even with a thousand messages, works offline from a local cache and is fully keyboard-controlled (arrows, Enter, Delete to Trash, Ctrl+Shift+U read/unread, Ctrl+F filter, Ctrl+R fetch). **Adding an account** needs only an e-mail address and password: server settings are found automatically like in Thunderbird (provider autoconfig, ISPDB, MX, DNS SRV, verified guessing), with manual setup as a fallback. **Security:** TLS always with certificate verification (no "continue anyway"), the password only in the keyring, never in a file; a wrong password is not retried; HTML messages shown as text without scripts, images or remote content (no tracking pixels). IMAP4rev1/rev2 with CONDSTORE and QRESYNC, MIME with Czech, German and Ukrainian character sets, attachments can be saved. - **The install count (countme) can no longer be inflated so easily** (server change, deployed by the maintainer; `luxos-docs` 64, the LuxOS usage page): one IP address could add a new "computer" for every combination of version and channel – the server accepted any X.Y.Z version (even 99.999.999), so with the limit of 60 requests per hour one address could add about 10,000 fake counts a week and junk versions showed up. With IPv6 every address also counted separately, and anyone with a /64 network (an ordinary home computer) could add counts without limit. Now each network – an IPv4 address, or an IPv6 /64 prefix (IPv4-mapped and NAT64 addresses count as that IPv4 address) – is counted **at most once a week, whatever it sends** (the first request of the week wins; a real computer sends once a week). Only **released LuxOS versions** are accepted, plus the next ones that staging reports before a release, so releasing 1.0.2 loses nothing; anything else gets an error and old junk is no longer shown. When a week's total jumps above ten times the previous week, the service logs one line (no IP addresses) so the maintainer notices. Privacy is unchanged: only weekly counters on disk, the weekly key only in memory, no request logs. Many different addresses (botnets, rotating proxies) cannot be stopped without identifying computers – the website and the documentation now say so honestly ("an approximate lower bound"). The public pages no longer show the exact request format, only what is sent; `lux config countme` still shows the exact request locally.
